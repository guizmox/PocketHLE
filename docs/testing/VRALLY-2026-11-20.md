# V-Rally: moving panorama seam (20 November 2026)

Status: excessive panorama motion traced to unpaced native GDI painting.
A shared paint-completion frame-limit correction is included and validated
on the headless ARM path. The asset
edge and line-carry behavior are separate from this timing defect.
Base: `b24d80122d4dc7607dce69e1a8348f918b75a99d`, branch `snapshots`,
with the cumulative 0.5.0 working changes.

## Fixture and reproduction

The supplied ARM CAB installs `V-Rally.exe` and `data.chk`:

| File | SHA-256 |
| --- | --- |
| V-Rally.exe | d0f5282d4cba432a9116062e7d706252f837f0361bd86772f7ecd380b9d97a38 |
| data.chk | 35a724f5222b4af0c7cf815154d48c579dd9fac5cceedde3be4a2ca853c391cc |

The reported defect is a moving discontinuity in the mountain panorama when
turning. A 64-second native ARM run entered a race and exercised left/right
steering. The supplied 114-frame video also shows the panorama in the preview.
This executable generates an indexed bitmap on the guest ARM CPU and presents
it through GDI (`CreateBitmap`, `CreatePatternBrush`, `PatBlt`); it does not use
OpenGL ES for this image.

## Boundaries checked

1. Twelve guest-produced 240×320 bitmaps, captured immediately after
   `CreateBitmap`, matched the following displayed images exactly after the
   selected palette and RGB565 conversion: zero differing pixels in every pair.
   This excludes an additional pattern-brush/presentation corruption for those
   samples, not every possible GDI operation.
2. Resource 21 was independently decompressed from `data.chk` at offset 212115.
   Its 9774 compressed bytes produce the declared 16652 bytes. Every decoded
   byte matches the live guest resource. The resource contains an eight-byte
   directory, a four-byte bitmap header, and 208×80 indexed pixels.
3. The original guest panorama blitter at `0x11e4c` was replayed for all 208
   horizontal phases on Unicorn's SA1110, PXA255, ARM926 and Cortex-A15 models.
   All 832 cases match the independently calculated byte-copy result. No
   unaligned word read occurred during these copies. Old ARM unaligned-load
   behavior therefore does not explain this particular copy.
4. The complete background prefix (`0x1ebdc..0x1ecd8`), including resource
   lookup, signed phase normalization, sky filling and the bitmap copy, was
   replayed at 79 positions spanning negative phases, ordinary positions and
   wraparound, on the same four models: 316 cases, zero differing pixels.
   Every replay was required to reach the expected stop PC. The Cortex-A15
   replay executed PocketHLE's actual native SDIV/UDIV thunks; the older models
   used arithmetic hooks implementing truncation toward zero and its remainder.
5. The camera update prefix (`0x1cabc..0x1ccf0`) was replayed from the captured
   race state with seven synthetic signed steering values, including zero and
   both directions, on all four models. All 28 results agreed. This checks the
   phase calculation for that state, not the entire game's physics. Native
   division optimization did not change either this calculation or the full
   background output in the tested cases.

## What the executable actually draws

The bitmap header is `01 00 1a 0a`. The executable derives its dimensions by
multiplying the last two bytes by eight: **208×80**. It nevertheless copies
**240 bytes per destination row**. With horizontal phase `p`, the source span
for row `r` starts at `image + 4 + r*208 + p` and continues for 240 bytes.
It crosses into the next source row rather than restarting at the beginning of
the same row. The visible row boundary is therefore at `208-p` when inside the
viewport. The resource's two horizontal edges also do not form a perfect seam.

The caller at `0x1ebdc..0x1ecd8` additionally computes
`q = (p + 240) / 208`, moves the destination down by `q`, and reduces the copied
height by `q`. Consequently this vertical adjustment changes by one pixel when
the horizontal phase crosses 176. These operations occur inside the supplied
game executable, before any PocketHLE graphics API receives the finished image.

The live trace covered 6480 background updates. All normalized phases remained
within 0..207; consecutive circular phase changes were between zero and minus
six. No out-of-range jump was observed in this run.

## Resource selection and screen-query follow-up

All 87 resource blocks decode to their declared lengths. Tracks 0..9 select
resources 14..23 directly at `0x1dddc..0x1de68`, using `state+0xdb8`;
track 7 is Corsica and selects resource 21. There is no screen-query fallback
in this selector. The ten panoramas have widths 216, 320, 344, 240, 240, 400,
328, 208, 328 and 256; these are original resource dimensions, not resolution
variants of one picture.

The live GX properties are internally consistent: 240×320, xPitch=2,
yPitch=480, 16bpp, ffFormat=0x80 (RGB565). The executable always creates a
240×320, one-plane, eight-bit presentation bitmap. It does not import
GetSystemMetrics, GetDeviceCaps, ExtEscape or dynamic library lookup for an
alternate screen query. Its GetClientRect(NULL) failure does not determine the
bitmap dimensions; SPI_GETOEMINFO only tests an HP-specific presentation flag.
No wrong-resolution resource selection was found.

An additional diagnostic ARM interpreter, independent of Unicorn, executed
the original blitter for all 208 phases and the complete background prefix at
15 boundary/wrap positions, with zero differing pixels. This reinforces the
copy result without mistaking different Unicorn CPU models for independent
implementations.

**Correction to the earlier hypothesis:** copying across source rows alone is
not evidence that the asset is broken. The caller explicitly adjusts position
and height to bound these reads. For Corsica, next-row edge continuity is
slightly better than same-row wrapping; another track benefits substantially
from next-row wrapping. This is consistent with an intentional cheap scrolling
layout, although the original author's intent has not been established.

## Excessive motion: paint-loop timing

The panorama's final phase increment at `0x1ccbc..0x1ccec` is frame-based:

```text
phase_delta = wrapping(car[0x14] * state[0xdc8] * 31)
              / (state[0xe74] << 9)
```

The signed quotient truncates toward zero. This expression has no elapsed-time
factor. A WM_PAINT at `0x2333c` calls `0x22a94`, which reads the real tick count
through its native GetTickCount thunk, updates elapsed-time state for other
simulation work, and unconditionally calls the race update and draw methods.
It then paints through GDI and invalidates the window again at `0x23360`.
There is no SetTimer/Sleep throttle on this path. Each additional paint advances
the background even when other simulation code already uses elapsed time.

The earlier per-call check (no jump larger than six pixels) therefore missed
an important distinction: a small displacement applied several hundred times
per second still rotates the panorama excessively. The user reports correct
motion on PalmOS; that is a useful behavioral reference, but a different port
cannot establish the exact intended PocketPC frame rate.

A corrected headless harness repeats the same real input schedule, entering a
race, holding acceleration and exercising both steering directions. Its install
mount now matches the production Desktop/Android mount order before the save
overlay; a missing harness mount had initially prevented CFile from opening
`data.chk`. No production mount change was required.

| Diagnostic run | Mean background updates/s | Peak absolute panorama pixels/s |
| --- | ---: | ---: |
| Existing unpaced native GDI loop | 403.3 | 2229 |
| Diagnostic 17ms publication spacing | 57.3 | 162 |
| Production correction, selected limit 60 FPS | 54.3 | 224 |
| Production correction, selected limit 20 FPS | 19.8 | 80 |

Each run lasts 64 seconds. Statistics use complete one-second buckets after
tracing begins at 45 seconds. The scheduling experiment changes the simulation
trajectory as well as rendering frequency; the peak pixel-rate ratio is not a
universal speedup or an exact matched-state comparison. It demonstrates that
publication cadence controls the reported excess motion. The diagnostic delay
is not production code and is excluded from the source patch.

The generic correction runs at a completed BeginPaint/EndPaint transaction
when a positive game FPS cap is selected. It does not sleep after each GDI
primitive, cap empty/offscreen transactions, or add another wait after an actual
GX/EGL presentation. Unlimited retains its existing behavior. The same shared
Rust handler is called by Desktop and Android. No UI setting, resource rewrite
or game-address rule was introduced. A frame-based animation can still move
faster at 60 than at 20 FPS; this correction honors the selected rate rather
than claiming to recover the original device cadence automatically. Native WM_PAINT
is not inherently a Windows guarantee of 60Hz; this is the emulator's explicit
user-selected limit, not a fabricated API timing guarantee.

Primary API references:
[BeginPaint CE3](https://learn.microsoft.com/en-us/previous-versions/ms959643(v=msdn.10))
and [InvalidateRect CE3](https://learn.microsoft.com/en-us/previous-versions/ms915258(v=msdn.10)).

## Implementation and validation

The paint transaction records its destination revision and completed-present
count at BeginPaint, before a native erase callback. EndPaint uses the existing
cooperative display deadline when visible native drawing changed and a
positive cap is selected. It preserves the transaction and original deadline
across scheduler retries. Another completed swap or a destroyed/hidden window
cancels that transaction's pending wait. Selecting an empty, unpainted backing
bitmap alone is not a new image. Arbitrary paint updates remain IPS telemetry;
no synthetic completed-game-frame counter is added.

The revision anchors are host-only. Serialization excludes them, and direct
in-memory GDI restore explicitly clears them. Guest update regions, pixels,
callback registers and pending guest messages keep their existing snapshot
state. The WinCE section remains 11; this pacing change does not invalidate
existing section-11 slots.

Five targeted regression tests cover direct-screen/window-backing waits and
stable retries, empty/hidden/offscreen/unrelated memory-only work (including a
new empty selected bitmap), uncapped/Unlimited/already-presented paths, wait
cancellation, and serialized/in-memory snapshot reset.

Final-source native smoke runs with a 60 FPS selection reached MoonGBA's menu,
Prey gameplay, the responsive BIA sound choice followed by its title image, and
Stuntcar's name-entry screen. Ultima restored the previously generated section-11
slot and continued rotating under a stationary held stylus. These short runs do
not establish exhaustive gameplay compatibility. Headless audio output is not
enabled and native GPU testing uses Mesa; no fresh Android APK/device run is
claimed for this source-only follow-up.

The final source passed 1253 Rust unit tests (799 WinCE, 420 kernel, 34 core);
37 tests requiring additional contexts/hardware remain ignored. Rust 1.90
formatting and git whitespace checks pass. Desktop and Android JNI host
compilation checks pass with Unicorn and optional host audio/static video
disabled. A fresh native CLI probe was compiled for the gameplay checks.

Temporary ARM hooks, the publication-delay experiment and the native runtime
probe are excluded from the source tree and package.

## Remaining uncertainty

Matching the game's instructions and resource data does **not** prove that the
result matches a physical PocketPC. A native-device capture of this same build
would distinguish an original asset/blitter limitation from an upstream
emulation difference not covered by these measurements. In particular, the
four Unicorn CPU models share an implementation and are not four independent
hardware references.

Do not compensate by altering arbitrary GDI bitmaps, changing the global ARM
model, or patching this game's addresses in production. None is justified by
the measurements. The global native arithmetic thunks also use ARMv7 divide
instructions, so selecting an older CPU globally would require separate work.
Temporary game-address probes and captured proprietary resources are excluded
from the source tree.
